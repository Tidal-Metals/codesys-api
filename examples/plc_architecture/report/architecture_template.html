BCNF PLC program: architecture redesign

2026-10-19 · Proposal · Based on the architecture review of PLC_BCNF_4_16_26.project and the MQTT bench tests

Summary
  • Two tasks instead of one. A high-priority control task runs inputs, alarms, interlocks and outputs; a lower-priority comms task runs MQTT. They exchange data only through a command queue, an acknowledgement queue and a snapshot, so communication can never delay or reorder control logic.
  • A fixed seven-step scan in the control task, and one owner for every variable. Behaviour no longer depends on which line happens to run last.
  • A tag table instead of per-tag code. Tags are rows in a table generated from the config sheet; scaling, quality, alarms and publishing are loops over it. Adding a tag means adding a row, not editing six places.
  • Every value has a quality, and every command gets an answer. Lost communication, stale or out-of-range values become visible and fail safe; commands are queued, validated, applied and acknowledged by id.
  • Outputs are request AND permit. Commands set requests, interlocks set permits, and one step writes the outputs. A bypass is time-limited and needs a local key switch; nothing bypasses an E-stop.
Who this is for. The engineer who will build the next version, and anyone reviewing it. Each section says what the piece does, why it is shaped that way, and shows the code. Short "Concept" boxes explain the PLC ideas it relies on; there is a glossary at the end.

Why change: the current structure

The current program does everything in one task, in an order that grew line by line rather than being designed. Each problem in the architecture review traces back to that:

  • Communication and control share one scan. String building (2.6 ms every scan, measured), message parsing and two MQTT clients run between the interlocks, in the same 50 ms task.
  • The order of lines decides behaviour. Alarms read inputs before they're normalized; commands are applied after the interlocks; several variables are written in two places.
  • Commands go through a one-message mailbox with no queue, no validation, no freshness check and no acknowledgement; a repeat is recognized by its text, so a legitimate retry can be dropped.
  • Nothing tracks whether a value is real. A failed Modbus slave, a silent remote PLC or a division by zero looks like a normal number.
  • Per-tag code everywhere. Each tag appears in about six places; the same pattern at 2,000 tags would be tens of thousands of lines, and copy-paste slips (like a command handled twice) come with it.

Design principles

Control never waits for comms. Separate tasks; the control task has the higher priority and its own data.
One owner per variable. Exactly one place writes each variable; everyone else reads.
A fixed order per scan. Inputs, commands, values, alarms, permissives, outputs, snapshot. Always.
Data, not code. Tags are table rows generated from the config sheet; logic is loops over the table.
Every value carries a quality. When in doubt, alarms and interlocks fail safe.
Every command gets an answer. Accepted or rejected, with a reason, matched by id.
Work when something happens. Build messages once per publish, parse once per message, not every scan.
Requests and permits are separate. Commands ask, interlocks allow, one step decides the output.

Tasks and hand-over

The program runs as two cyclic tasks. The control task owns everything that touches the plant; the comms task owns everything that touches the network. They share three things, each with a single writer on each side.

Concept: task priority. CODESYS runs the highest-priority task that is due. When the control task's 50 ms comes round while the comms task is running, the comms task is paused, the control scan runs to completion, then the comms task carries on. That is why the comms task can afford a long message build and the control task never starts late. The flip side: anything the two tasks share can be read by one task while the other is half-way through changing it. The queues and the snapshot below exist to make that impossible.

The control scan: seven fixed steps

Every control scan runs the same seven steps in the same order. Each step reads what earlier steps produced and writes only its own results, so a value is never used before it is ready, and the order is written down in one place instead of emerging from line positions.

One owner per variable

Every variable has exactly one writer. When a variable has two, whichever runs last wins, and the behaviour changes when someone moves a line. In the current program an MQTT stop and the hardware input both write LSS_E_STOP, so the remote stop is overwritten within a scan.

Concept: "the last writer wins". In a PLC, a variable keeps whatever was last assigned to it in the scan. If an interlock sets P_1502 := FALSE on line 1010 and a command handler sets P_1502 := TRUE on line 144 but runs later, the command wins, whatever the interlock decided. Separating the request (written by the command step) from the output (written only by step 6) removes the race instead of depending on line order.

The tag table

Today each tag is code: a variable, a raw variable, scaling, alarm comparisons, a string-building line and a command branch, all written out by hand or by a spreadsheet. The new design makes each tag a row in a table, and the program a set of loops over it.

  • Generate the table, not the code. A script turns the config sheet into the TagConfig initializer and the named index constants, so names and indices can't drift apart. Hand-written logic refers to tags by those constants (Tags[GVL_Tags.TAG_AIT_1508]).
  • Memory, roughly: a TagConfig row is about 64 bytes and a Tags row about 40; with the snapshot and the publisher's change history, around 150 bytes per tag, so about 300 KB for 2,000 tags plus a message buffer of about 40 KB. Check this against the CPU's data memory before committing to 2,000 tags (these sizes are estimates; SIZEOF on the target gives the real ones).
  • Alarms as rows too. The skeleton shows one alarm by hand; the full design puts alarm definitions (tag, limit tag, direction, hysteresis, delay) in a second generated table, evaluated in a loop.

Outputs: request AND permit

An output is on when someone asked for it and the interlocks allow it. The two are computed in different steps and combined in exactly one place.

  • A trip clears the request, so the pump doesn't restart by itself when the alarm clears; it needs a new start command. The request is cleared in step 2 after the commands, and a start is refused (INTERLOCKED) unless the permit is on and the start was sent after the permit came back, with the clock-skew margin. So a start queued, delayed or retried across a trip can't restart the pump afterwards.
  • Bypass is per actuator (the config sheets define a <tag>_Bypass request for each actuator). It also needs the local key-switch input and expires on its own (BypassUntilMs; the skeleton shows one bypass for brevity). It can lift alarm trips; it can never lift an E-stop.
  • E-stops from the network count as active when their signal goes stale or the link fails. Whether that is right for each remote stop is a decision for the team; hard-wired E-stop circuits stay outside the PLC either way.

Commands: queued, validated, answered

A command is a request to change a writable tag: a setpoint, a start or stop. Today's path keeps only the latest message and recognizes repeats by their text. The new path keeps every message, checks it, applies it in the control task and answers it.

PartDesign
Message<id>,<tag>=<value>,<sent_ms>. The bridge is the only sender: HMIs and scripts ask the bridge, which checks who they are, assigns the id and stamps sent_ms from its own clock. One id space and one clock make retries and ordering well defined.
ReceiveFB_CommandReceiver implements the MQTT library's callback interface and pushes every message into the queue, instead of keeping only the latest one.
ValidateParsed only if the whole message arrived, and the id, value and timestamp are plain numbers short enough for their types (STRING_TO_REAL reads garbage as 0). Then: not a retry (below); known, writable tag; inside the tag's range, where NaN and infinity count as outside; then 0/1 for a BOOL, or a whole number for an INT, converted only once the value is known to be in range; the PLC clock is plausible; sent no more than 10 s ago and not in the future; queued no longer than 2 s; not older than the last command applied to the same tag; a start only while the equipment is permitted and sent after its last trip. Cross-checks such as "HH above H" belong here too.
ApplyCommands set values (start = 1, setpoint = 42.5), never toggle. A retry is the identical message sent again (same id, tag, value and sent_ms); a ledger of recent commands gives it the first answer, and it is never applied twice. An older command can't overwrite a newer one (OUT_OF_ORDER), so a delayed start can't undo a later stop.
AnswerEvery command is acknowledged as <id>:<result> on plc_acks/<plc>: accepted, malformed, unknown tag, not writable, out of range, too old, out of order, interlocked, clock not synchronized. An acknowledgement batch stays until the broker confirms it.
OverloadA full command queue drops the command without an answer. A full acknowledgement queue never holds a command back, so a stop is applied even then, and its answer is dropped. Either way the sender times out and retries the same message, and the ledger answers it. At most 10 commands are applied per control scan. The ledger (64 entries in the skeleton) must hold every command the bridge may send within the 10 s validity window; the bridge rate-limits to that, and a counter shows when it doesn't.
AuthorityFreshness is not authentication. Who may command which PLC is decided by the broker: per-PLC credentials, topic ACLs on plc_commands/<plc>, and TLS where the network allows. Today's broker accepts anonymous clients, so this is a decision to make before commands carry more weight.
Concept: why a queue between tasks needs care. The comms task may be paused in the middle of adding a command when the control task starts its scan. The queue is written so that can't go wrong: the producer fills a slot completely before moving its own index, the consumer only reads slots behind that index, and each side writes only its own index. No locks are needed for one producer and one consumer, as long as both tasks run on the same CPU core; on a multi-core controller, pin both tasks to one core or use the runtime's atomic operations and memory barriers for the indices.

Quality: knowing when a value is real

Every tag carries a quality next to its value. It is set from the source's health and age in step 1, and from range checks in step 3. Alarms, interlocks, publishing and the HMI all see it.

  • Where health comes from: Modbus slave diagnostics (the master reports an error per slave), local I/O module diagnostics, the MQTT connection, and the age of the last sample from each remote PLC. Source adapters in the control task set SourceIsHealthy and SourceUpdatedAtMs; values that arrive in the comms task (other PLCs over MQTT) reach them through a queue as complete records, never by writing those variables from the other task. A source with no sample since start-up is INIT, not GOOD.
  • Silence is not staleness. With report-by-exception a healthy source can send nothing for a while. Each remote PLC therefore publishes a heartbeat at least every few seconds, and freshness comes from that heartbeat (or per group of tags, where they are acquired independently), not from whether any value changed.
  • The last good value is kept and marked, rather than replaced by zero, so a dropout doesn't look like a real reading of 0.
  • Derived values inherit the worst quality of their inputs and become INVALID instead of dividing by zero.

Publishing from a snapshot

The comms task builds the outgoing message from a consistent copy of the tag table, sends only what changed (plus a periodic full refresh), spreads the build over several calls and uses one publisher. The measurements behind it are in the MQTT large-payload report.

@@publish_data@@ @@append_tag@@

Other PLCs' status (today's [ReadyTags = …] list) arrives the same way: as tag:value lines from each PLC, each PLC a source with its own staleness timeout, so a silent neighbour becomes STALE instead of keeping its last state forever. Their heartbeat is what keeps them fresh between changes.

  • History moves only when a message went out. Which tags were sent is committed after the publisher reports done; a message that didn't fit changes nothing, and the next one is a full refresh. So is the next message built after a reconnect.
  • A slow message is waited for, not abandoned. The library has no cancel: once started, it keeps a message until the broker has it, resends it after a reconnect, and reads the buffer through its pointer all that time. Its SendTimeout output only says the message is slow, so the code counts it and leaves the buffer, the snapshot and the history alone until done.
  • Bad values go out as NaN. A tag that isn't GOOD, or holds NaN or infinity, is published as NaN instead of being pushed through an integer conversion, which can fault. The bridge needs to treat NaN as bad quality until quality has its own place on the wire.
  • The buffer fits the worst case. The generator computes the largest possible message for the table (every tag, longest values) and sizes the buffer from it, or refuses the table. 2,000 tags with 15-character names already need about 36 KB.
  • The publisher re-arms. The MQTT library starts a message on a rising edge of send, so the code makes sure it sees FALSE between two messages.

Migration plan

  1. Quick wins in the current program: call StringPublication() only when publishing (saves 2.6 ms per scan), fix the duplicated command handler and the execution order of inputs and alarms.
  2. Two tasks: move MQTT into its own lower-priority task with one client. The interlock logic is untouched.
  3. Tag table: generate TagConfig from the config sheet and run steps 1, 3 and 4 as loops, first in parallel with the old code, comparing results.
  4. Outputs: requests and permits, one writer per output, bypass with key switch and expiry.
  5. Commands: the queue, ids, validation and acknowledgements. This needs the HMI or bridge to send ids and read acks.
  6. Quality and publishing: source health, staleness, tag:value with report-by-exception; then remove the old code.

The skeleton

All code in this document is taken from a skeleton in the codesys-api repo, examples/plc_architecture/, which compiles without errors or warnings against the MQTT library used on site (CODESYS V3.5 SP22, MQTT 1.2.0.7). It has four example tags; it has not run on a PLC. Not in the skeleton: the source adapters, the alarm and permissive tables, the bypass command path and its logging, setpoint persistence, and quality on the wire. An independent review (Codex) of an earlier version found defects in command retries, trip clearing, NaN handling, freshness, acknowledgement loss and the publisher's re-arming. A second review found that a slow publication could be overwritten, that a conversion could fault before a command was rejected, that retries were matched by id alone, that a congested acknowledgement queue could hold back a stop, and that clocks from several senders were compared. The code shown here has those fixed. The second review also confirmed that the items listed as not in the skeleton are still open. It reuses AppendZ from the MQTT large-payload example. Agents writing or generating code for this structure follow docs/plc-architecture-for-agents.md in the same repo: the invariants, the config-sheet-to-table mapping and the generator workflow.

Glossary

TaskA schedule that calls programs: cyclic every N ms, with a priority. Higher-priority tasks interrupt lower ones.
ScanOne run of a task's programs from top to bottom. Variables keep their values between scans.
Program / FB / functionA program exists once; a function block is a type with instances, each with its own memory; a function has no memory between calls.
Action / methodNamed pieces of code inside a program or FB, sharing its variables. Used here to split the scan into its seven steps.
GVLGlobal variable list: variables every task can see. qualified_only forces GVL_Tags.Name, which makes the origin obvious.
I/O mappingBinding a variable to an input, output or Modbus channel in the device tree; the runtime copies values at the start and end of the task that owns the device.
Interlock / permissiveLogic that decides whether equipment may run, independent of whether someone asked it to.
Report by exception (RBE)Sending a value only when it changed (beyond a deadband), plus periodic refreshes.
QoS 0 / 1MQTT delivery: 0 = sent once, no confirmation; 1 = confirmed by the broker (PUBACK), resent if not.
Single-producer / single-consumerA queue with exactly one task adding and one task taking, which can be made safe without locks.
