Summary
  • The MQTT library has no 255-character limit. The cap comes from CODESYS's Standard string functions (CONCAT and friends), which return at most 255 characters, and from passing payloads through STRING(255) variables. That's why declaring a STRING(8000) didn't help.
  • One publisher is enough. Built with a pointer append instead of CONCAT, a single message carried 500 and 1,100 values (7.9 KB and 17.6 KB) to the HQ broker. All @@total_messages@@ messages were exact, @@total_values@@ values checked, with no gaps or timeouts. We don't need 40 parallel publishers.
  • Sending is cheap; building is not. The library sends the payload over several scans at no more than 2.4 ms per scan. Building the text costs about 30 µs per value, all in one scan. At 1,100 values that pushed a 50 ms task 25 ms late (with the demo's CONCAT comparison copy included). Run the MQTT build in its own lower-priority task.

Where the 255-character limit comes from

The BCNF project (PLC_BCNF_4_16_26.project) builds each payload with CONCAT into a STRING(255) and hands it to FirstPublish through STRING(255) inputs. Both cut the text at 255 characters before the MQTT library ever sees it.

The library itself measures string payloads by scanning to the terminating zero and splits large payloads across its TCP buffer. Excerpts from the 1.2.0.7 source, dumped from the installed library:

@@library_snippet@@

The maintainer says the same on GitHub. In issue #17 he notes that the library has no string-size limit and that CODESYS's own string functions only handle 255 characters, which is why the library has its own pointer-based helpers. Issue #76 ("Limited String payload size") ended with long JSON payloads working; the confusion there was the debugger showing only 80 characters behind a pointer. COM_CONFIG.MaxPayloadSize (default 2000) limits received messages only.

About the 255 you noticed in the results: that was deliberate. Alongside the real payload, the demo builds the same text with CONCAT into a STRING(8000) and publishes it on raw_data_demo/concat. That reproduces what the team tried. It came out at exactly 255 characters every time (LastConcatLength = 255 on the PLC, and 255 bytes on the wire), cut off mid-line as a clean prefix of the full message. The pointer-built payload in the same scan, from the same lines, arrived complete.

Test setup

Each message is a set of lines the PC can recompute exactly: DEMO_SEQ:<seq>, DEMO_COUNT:<n>, then DEMO_V1 to DEMO_Vn with value seq × 1000 + i, then DEMO_END:<seq>. A missing trailer, wrong value or skipped sequence number fails the check. The TAG:value line format is the one the bridge parses on raw_data.

Recipe: publishing a large payload from CODESYS

  1. One buffer per message, sized for the largest payload plus margin, e.g. LargePayload : STRING(20000). At about 16 bytes per line, 20,000 bytes holds about 1,150 values.
  2. Build the text with a pointer append (AppendText below), not CONCAT. CONCAT and REAL_TO_STRING are fine for one short piece under 255 characters; only the running total has to avoid them. Keep the current length in a variable so each append doesn't rescan the buffer.
  3. Hand the publisher a pointer to the buffer: PayloadString := ADR(LargePayload), PublishAsString := TRUE. Don't copy the payload through STRING(255) inputs or variables on the way.
  4. Leave the buffer alone while a publish is in flight. The library reads it through the pointer over several scans. Rebuild only after done or SendTimeout.
  5. Treat done and SendTimeout as one-scan pulses. Clear each publisher's own request on either. Don't wait for several publishers' done in the same scan; that's the stall risk in BCNF's FirstPublish.
  6. Turn on dynamic memory in Application Properties › Build (the demo uses 100,000 bytes, BCNF already has 50,000). Without it the library won't compile.
  7. Don't name a variable Mqtt: ST names are case-insensitive, so it hides the MQTT library namespace.
  8. Keep the build out of the control task. Put the build and publish in a lower-priority task (e.g. 100 ms) that copies a snapshot of the values first, or spread the build over several scans. See Performance.

What the numbers say

  • Sending large payloads is cheap. The client copies the payload out over several scans and never took more than 2.4 ms in one scan, even at 17.6 KB.
  • The build is the expensive part: about 30 µs per value (1.9 ms for 50, 15 ms for 500, 33 ms for 1,100), almost all of it number-to-text conversion and the short CONCATs that format each line. It all happens in one scan.
  • At 1,100 values the scan overran. Build plus the demo's CONCAT copy came to 74 ms, so one scan per publish started 25 ms late. Without the comparison copy the build alone is 33 ms, two thirds of the 50 ms cycle before any interlock logic runs. In BCNF that would likely overrun too.
  • Latency floor of 4–5 scans. Even a 727-byte message took 5 scans (about 200 ms) from request to PUBACK, because of the library's state machine and the QoS 1 handshake. 17.6 KB took 13–14 scans (about 0.55–0.6 s). At a 50 ms task that's roughly 25–30 KB/s per client, plenty for 10–20 KB once a second.
  • 40 small publishers wouldn't be faster. They'd do the same formatting work, and each message pays the 4–5 scan handshake through the one client.

Recommendations for BCNF

  1. Move the MQTT build and publish into a separate lower-priority task (e.g. 100 ms), copying a snapshot of the published values at the start of each build. A long build then can't delay the interlock task. This is the main fix.
  2. If it has to stay in the main task, build over several scans (e.g. 200 lines per scan) and publish when the buffer is complete.
  3. Format with fewer intermediate strings: append the name, the colon and the value straight into the buffer instead of nesting CONCATs. I'd expect this to cut the build time noticeably, but I haven't measured it.

What worked, what didn't

Worked first time: the unmodified MQTT library sending 17.6 KB in one message; QoS 1 publishing to the HQ broker without credentials; the bounded pointer append; downloading to the bench PLC with a full download plus boot application; changing the payload size online without a new download.

Not tested

  • Bridge ingest. The demo used its own topics, so the sparkplug-bridge never parsed these messages. Its raw_data parser splits a payload on newlines and has no size check of its own, but the broker's and client's packet-size limits weren't checked and a large ingest through it hasn't been run.
  • BCNF's real load. The bench application does nothing besides MQTT. BCNF's interlock logic, serial Modbus and task layout will add to the scan.
  • Faults. No broker restart, cable pull or network congestion tests. The library's reconnect and the SendTimeout path weren't exercised.
  • Sample size. One 35 s run per size, about 7 messages each. The maxima look stable across runs, but this is not a soak test.
  • QoS 0 (what BCNF uses today) wasn't measured; the demo uses QoS 1 so done means the broker acknowledged the message.
