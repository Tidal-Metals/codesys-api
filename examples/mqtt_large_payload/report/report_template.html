Summary
  • The MQTT library has no 255-character limit. The cap comes from CODESYS's Standard string functions (CONCAT and friends), which return at most 255 characters, and from passing payloads through STRING(255) variables. That's why declaring a STRING(8000) didn't help.
  • One publisher is enough. Built with a pointer append instead of CONCAT, one message carried up to 1,100 two-decimal values (19.7 KB) to the HQ broker once a second, at QoS 0 and QoS 1. All @@total_messages@@ messages were correct, @@total_values@@ values checked, with no gaps or timeouts. We don't need 40 parallel publishers.
  • It fits in a 50 ms task, but the build is the cost to watch. With production settings (BCNF-style REAL formatting, one publish a second, no extra work), building the text takes about 36 µs per value, all in one scan: 19 ms for 500 values, 40 ms for 1,100. Where the 255-character limit comes from

The BCNF project (PLC_BCNF_4_16_26.project) builds each payload with CONCAT into a STRING(255) and hands it to FirstPublish through STRING(255) inputs. Both cut the text at 255 characters before the MQTT library ever sees it.

The library itself measures string payloads by scanning to the terminating zero and splits large payloads across its TCP buffer. Excerpts from the 1.2.0.7 source, dumped from the installed library:

The maintainer says the same on GitHub. In issue #17 he notes that the library has no string-size limit and that CODESYS's own string functions only handle 255 characters, which is why the library has its own pointer-based helpers. Issue #76 ("Limited String payload size") ended with long JSON payloads working; the confusion there was the debugger showing only 80 characters behind a pointer. COM_CONFIG.MaxPayloadSize (default 2000) limits received messages only.

The CONCAT control copy. To reproduce what the team tried, the demo can also build the same text with CONCAT into a STRING(8000) and publish it on raw_data_demo/concat. In the first runs it came out at exactly 255 characters every time (LastConcatLength = 255 on the PLC, @@concat_messages@@ messages of 255 bytes on the wire), cut off mid-line as a clean prefix of the full message. The pointer-built payload in the same scan, from the same lines, arrived complete. This is a demonstration, not production work, so it's now off by default (IsConcatControlEnabled) and is not part of the performance numbers.

Test setup

Each message is a set of lines the PC can recompute: DEMO_SEQ:<seq>, DEMO_COUNT:<n>, DEMO_FORMAT:REAL or INT, then DEMO_V1 to DEMO_Vn, then DEMO_END:<seq>. Value i is seq × 1000 + i as an integer, or that divided by 100 as a two-decimal REAL formatted with the same REAL_TO_STRING(... TRUNC ...) expression BCNF uses. Integers must match exactly; REALs must be within ±0.006, since the PLC formats single-precision floats. A missing trailer, wrong value or skipped sequence number fails the check. The TAG:value line format is the one the bridge parses on raw_data.

Recipe: publishing a large payload from CODESYS

  1. One buffer per message, sized for the largest payload plus margin, e.g. LargePayload : STRING(30000). A two-decimal value line is about 18 bytes, so 30,000 bytes holds about 1,600 values.
  2. Build the text with a pointer append (AppendText below), not CONCAT. CONCAT and REAL_TO_STRING are fine for one short piece under 255 characters; only the running total has to avoid them. Keep the current length in a variable so each append doesn't rescan the buffer.
  3. Hand the publisher a pointer to the buffer: PayloadString := ADR(LargePayload), PublishAsString := TRUE. Don't copy the payload through STRING(255) inputs or variables on the way.
  4. Leave the buffer alone while a publish is in flight. The library reads it through the pointer over several scans. Rebuild only after done or SendTimeout.
  5. Treat done and SendTimeout as one-scan pulses. Clear each publisher's own request on either. Don't wait for several publishers' done in the same scan; that's the stall risk in BCNF's FirstPublish.
  6. Turn on dynamic memory in Application Properties › Build (the demo uses 100,000 bytes, BCNF already has 50,000). Without it the library won't compile.
  7. Don't name a variable Mqtt: ST names are case-insensitive, so it hides the MQTT library namespace.
  8. Keep the build out of the control task. Put the build and publish in a lower-priority task (e.g. 100 ms) that copies a snapshot of the values first, or spread the build over several scans. See Performance.

What the numbers say

  • Every scan started on time, even at 1,100 values (19.7 KB). The longest gap between scan starts was 51.0 ms against a 50 ms interval.
  • The build is the cost: about 36 µs per REAL value, all in one scan (2.5 ms for 50, 18.6 ms for 500, 39.5–40.0 ms for 1,100). Integers are about 13% cheaper (34.4 ms for 1,100), so most of the time goes into number-to-text conversion and the short CONCATs that format each line, not the append.
  • Sending is cheap. The MQTT client never took more than 2.5 ms in one scan while copying a 19.7 KB payload out.
  • QoS 1 adds about 150 ms (3 scans) for the PUBACK round trip: 1,100 values took 414 ms at QoS 0 and 563 ms at QoS 1. Both finish well inside the one-second period.
  • For BCNF: the 40 × 250 characters it needs is about 10 KB, roughly 550 values in this format, so expect about 20 ms of build in the scan that publishes, on top of the interlock logic. The bench PLC runs nothing else, so it can't show how much headroom BCNF's own scan leaves.
  • 40 small publishers wouldn't be faster. They'd do the same formatting work, and each message pays the library's handshake through the one client.

Recommendations for BCNF

  1. Put the MQTT build and publish in a separate lower-priority task (e.g. 100 ms) that copies a snapshot of the published values first. On the bench a 1,100-value build fits a 50 ms scan, but BCNF's interlock logic shares that scan; a separate task keeps a 20–40 ms build away from control code entirely.
  2. If it has to stay in the main task, build over several scans (e.g. 200 values per scan) and publish when the buffer is complete.
  3. Format with fewer intermediate strings: append the name, the colon and the value straight into the buffer instead of nesting CONCATs. I'd expect this to cut the build time noticeably, but I haven't measured it.

What worked, what didn't

Worked first time: the unmodified MQTT library sending 19.7 KB in one message; QoS 0 and QoS 1 publishing to the HQ broker without credentials; the bounded pointer append; downloading to the bench PLC with a full download plus boot application; changing the payload size online without a new download.

Not tested

  • Bridge ingest. The demo used its own topics, so the sparkplug-bridge never parsed these messages. Its raw_data parser splits a payload on newlines and has no size check of its own, but the broker's and client's packet-size limits weren't checked and a large ingest through it hasn't been run.
  • BCNF's real load. The bench application does nothing besides MQTT. BCNF's interlock logic, serial Modbus and task layout will add to the scan.
  • Faults. No broker restart, cable pull or network congestion tests. The library's reconnect and the SendTimeout path weren't exercised.
  • Sample size. One 45 s window per setting, about 42 messages each. Build times agreed within 0.5 ms between the QoS 0 and QoS 1 runs, but this is not a soak test.
  • Other task intervals. Only the 50 ms MainTask was measured. A different interval changes the scan budget and how many scans a publish takes.
