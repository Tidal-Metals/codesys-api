Where the 255-character limit comes from

The BCNF project (PLC_BCNF_4_16_26.project) builds each payload with CONCAT into a STRING(255) and hands it to FirstPublish through STRING(255) inputs. Both cut the text at 255 characters before the MQTT library ever sees it.

@@bcnf_snippet@@

The library itself measures string payloads by scanning to the terminating zero and splits large payloads across its TCP buffer. Excerpts from the 1.2.0.7 source, dumped from the installed library:

@@library_snippet@@

The maintainer says the same on GitHub. In issue #17 he notes that the library has no string-size limit and that CODESYS's own string functions only handle 255 characters, which is why the library has its own pointer-based helpers. Issue #76 ("Limited String payload size") ended with long JSON payloads working; the confusion there was the debugger showing only 80 characters behind a pointer. COM_CONFIG.MaxPayloadSize (default 2000) limits received messages only.

The CONCAT control copy. To reproduce what the team tried, the demo can also build the same text with CONCAT into a STRING(8000) and publish it on raw_data_demo/concat. In the first runs it came out at exactly 255 characters every time (LastConcatLength = 255 on the PLC, @@concat_messages@@ messages of 255 bytes on the wire), cut off mid-line as a clean prefix of the full message. The pointer-built payload in the same scan, from the same lines, arrived complete. This is a demonstration, not production work, so it's now off by default (IsConcatControlEnabled) and is not part of the performance numbers.

How the payload is built

This is where the demo differs from BCNF. The MQTT call is the same MQTTPublish with PayloadString := ADR(...); what changes is how the text gets into memory before that call, how many times it is copied, and how often it is rebuilt.

The two pipelines

What BCNF does today

Excerpts from PLC_BCNF_4_16_26.project, trimmed. Every group follows the same pattern: start a STRING(255), then one CONCAT for the separator and one for the value, for every value. The project has about 200 CONCAT calls in total.

@@bcnf_today@@

Four things in this code limit or slow it down:

  • Every CONCAT returns at most 255 characters. Once a group passes 255, the rest of it is dropped without an error. The setpoints are split into BCNF_SETPOINT_STRING_1 and _2, presumably to stay under that limit; more values means more groups, hence "40 publishers".
  • Every assignment into a STRING(255) also truncates silently, and each group is copied three times on its way to the publisher: into fullPayload_*, into the FirstPublish input and into fullPayloadN. Declaring any one of them bigger doesn't help while the others stay at 255.
  • Each CONCAT re-copies the whole string built so far, so a group costs more the longer it gets. The demo's append only copies the new piece.
  • StringPublication() runs every scan, although FirstPublish only sends about once a second. This one is measured below.

Measured: BCNF rebuilds its payload in every scan

The single biggest waste in BCNF's MQTT code, and the easiest to fix. FB_InterlockMatrix calls StringPublication() at the end of its body, and the FB runs in every 50 ms scan. So the seven payload strings — 103 values, 48 of them REALs, about 200 CONCAT calls — are rebuilt 20 times a second. FirstPublish sends them about once every 1.1 s, so @@bcnf_wasted@@ builds are thrown away unused.

AppendText, step by step

The whole technique is one small function. The caller owns a large STRING(n) buffer and a Used counter; AppendText copies one short piece to the end and moves the counter.

@@append_text@@
  • Capacity is SIZEOF(buffer). A STRING(30000) occupies 30,001 bytes, so the check Used + TextLength + 1 > Capacity always leaves room for the terminator.
  • The terminator is rewritten after every append, so the buffer is a valid string at all times. That's what the MQTT library relies on: it measures the payload by scanning to the zero byte.
  • Used is kept by the caller (VAR_IN_OUT) instead of measuring the buffer each time, so an append costs only the length of the piece, however big the payload already is.
  • All or nothing. If a piece doesn't fit, the function returns FALSE and writes nothing. The caller ANDs the results and skips publishing a message that didn't fit, so the bridge never gets half a payload.
  • The piece is a STRING(255) input, which is fine: only the running total needs to be large. That's why CONCAT and REAL_TO_STRING remain safe for formatting a single value or line.

When the buffer may change

The library doesn't copy the payload when send rises. It keeps the pointer and copies the text into its TCP buffer over the next few scans; at QoS 0 it reported done after 6 scans for 8.9 KB and 10 scans for 19.7 KB. Pitfalls with long strings in CODESYS

  • Standard string functions (CONCAT, LEFT, RIGHT, MID, INSERT, REPLACE, …) work on STRING(255). Use them on short pieces only.
  • Any STRING(255) on the path — a variable, an FB input, a function result — truncates without an error.
  • Passing a big STRING into an FB input copies all of it every call. Pass ADR() or use VAR_IN_OUT.
  • Changing the buffer while a publish is in flight sends a mix of old and new text.
  • Commas inside values would break the bracket format. REAL_TO_STRING doesn't produce them, but string tags would need escaping.

Test setup

Each message is a set of lines the PC can recompute: DEMO_SEQ:<seq>, DEMO_COUNT:<n>, DEMO_FORMAT:REAL or INT, then DEMO_V1 to DEMO_Vn, then DEMO_END:<seq>. Value i is seq × 1000 + i as an integer, or that divided by 100 as a two-decimal REAL formatted with the same REAL_TO_STRING(... TRUNC ...) expression BCNF uses. Integers must match exactly; REALs must be within ±0.006, since the PLC formats single-precision floats. A missing trailer, wrong value or skipped sequence number fails the check. The TAG:value line format is the one the bridge parses on raw_data.

Recipe: publishing a large payload from CODESYS

  1. One buffer per message, sized for the largest payload plus margin, e.g. LargePayload : STRING(30000). A two-decimal value line is about 18 bytes, so 30,000 bytes holds about 1,600 values.
  2. Build the text with a pointer append (AppendText below), not CONCAT. CONCAT and REAL_TO_STRING are fine for one short piece under 255 characters; only the running total has to avoid them. Keep the current length in a variable so each append doesn't rescan the buffer.
  3. Hand the publisher a pointer to the buffer: PayloadString := ADR(LargePayload), PublishAsString := TRUE. Don't copy the payload through STRING(255) inputs or variables on the way.
  4. Build once per publish, never every scan. Call the build from the publish timer, not from logic that runs in every scan; BCNF's every-scan rebuild costs about @@bcnf_build_mean_ms@@ ms per scan for nothing (measured).
  5. Leave the buffer alone while a publish is in flight. The library reads it through the pointer over several scans. Rebuild only after done or SendTimeout.
  6. Treat done and SendTimeout as one-scan pulses. Clear each publisher's own request on either. Don't wait for several publishers' done in the same scan; that's the stall risk in BCNF's FirstPublish.
  7. Turn on dynamic memory in Application Properties › Build (the demo uses 100,000 bytes, BCNF already has 50,000). Without it the library won't compile.
  8. Don't name a variable Mqtt: ST names are case-insensitive, so it hides the MQTT library namespace.
  9. Keep the build out of the control task. Put the build and publish in a lower-priority task (e.g. 100 ms) that copies a snapshot of the values first, or spread the build over several scans. See Performance.

What the numbers say

  • Every scan started on time, even at 1,100 values (19.7 KB). The longest gap between scan starts was 51.0 ms against a 50 ms interval.
  • The build is the cost: about 36 µs per REAL value, all in one scan (2.5 ms for 50, 18.6 ms for 500, 39.5–40.0 ms for 1,100). Integers are about 13% cheaper (34.4 ms for 1,100), so most of the time goes into number-to-text conversion and the short CONCATs that format each line, not the append.
  • Sending is cheap. The MQTT client never took more than 2.5 ms in one scan while copying a 19.7 KB payload out.
  • QoS 1 adds about 150 ms (3 scans) for the PUBACK round trip: 1,100 values took 414 ms at QoS 0 and 563 ms at QoS 1. Both finish well inside the one-second period.
  • For BCNF: the 40 × 250 characters it needs is about 10 KB, roughly 550 values in this format, so expect about 20 ms of build in the scan that publishes, on top of the interlock logic. The bench PLC runs nothing else, so it can't show how much headroom BCNF's own scan leaves.
  • 40 small publishers wouldn't be faster. They'd do the same formatting work, and each message pays the library's handshake through the one client.

Recommendations for BCNF

  1. Stop rebuilding the payload every scan. Call StringPublication() only in the scan that publishes. That saves about @@bcnf_build_mean_ms@@ ms in every 50 ms scan today, needs no other change, and can ship first (measurement and fix).
  2. Put the MQTT build and publish in a separate lower-priority task (e.g. 100 ms) that copies a snapshot of the published values first. On the bench a 1,100-value build fits a 50 ms scan, but BCNF's interlock logic shares that scan; a separate task keeps a 20–40 ms build away from control code entirely.
  3. If it has to stay in the main task, build over several scans (e.g. 200 values per scan) and publish when the buffer is complete.
  4. Format with fewer intermediate strings: append the name, the colon and the value straight into the buffer instead of nesting CONCATs. I'd expect this to cut the build time noticeably, but I haven't measured it.

tag:value at 2,000 tags

The positional publish map exists mostly to squeeze values under the old 255-character limit. Sending each tag:value as its own MQTT message was tried before and was slow, because each message pays the library's send handshake, a broker delivery and a separate bridge ingest. With the limit gone, all the tag:value lines can travel in one message, and the bridge ingests that directly: it splits a message on newlines and looks up each tag without a publish map (raw_ingest.go; from reading the code, not run end to end).

Report by exception: estimated savings

Today every value is sent every second whether it changed or not. With tag:value lines the PLC can send only the tags that changed — a BOOL or DINT that differs from the last value sent, a REAL that moved more than a deadband — plus a periodic full refresh so the bridge is never left holding a stale value (after a bridge restart, say). The publish map can't do this per tag: every position in a group line has to be filled.

These are estimates. How often tags change depends on the process, so the scenarios below are assumptions: BOOLs change rarely, DINTs (counters, states, setpoints) occasionally, REALs often unless a deadband filters out noise. What worked, what didn't

Everything we ran into, from building the demo through deploying and measuring it.

Worked first time: the unmodified MQTT library sending 19.7 KB in one message; QoS 0 and QoS 1 publishing to the HQ broker without credentials; the bounded pointer append; downloading to the bench PLC with a full download plus boot application; changing the payload size online without a new download.

Not tested

  • Bridge ingest. The demo used its own topics, so the sparkplug-bridge never parsed these messages. Its raw_data parser splits a payload on newlines and has no size check of its own, but the broker's and client's packet-size limits weren't checked and a large ingest through it hasn't been run.
  • BCNF's real load. The bench application does nothing besides MQTT. BCNF's interlock logic, serial Modbus and task layout will add to the scan.
  • Faults. No broker restart, cable pull or network congestion tests. The library's reconnect and the SendTimeout path weren't exercised.
  • Sample size. One 45 s window per setting, about 42 messages each. Build times agreed within 0.5 ms between the QoS 0 and QoS 1 runs, but this is not a soak test.
  • Other task intervals. Only the 50 ms MainTask was measured. A different interval changes the scan budget and how many scans a publish takes.

Pros and cons: tag:value vs publish_map

For the new system's ~2,000 tags, with the payload built once per publish by pointer append in either case. Numbers are from the bench tests above; RBE figures are estimates.

tag:value lines

Pros

  • No publish-map configuration on the bridge, and no position coupling: adding, removing or reordering a tag on the PLC can't shift other values onto the wrong tags.
  • Can report by exception: an estimated @@rbe_typical_kb@@ KB typical message instead of @@tv_bytes_kb@@ KB, about @@rbe_typical_build_ms@@ ms of build instead of @@tv_build_ms@@ ms.
  • Self-describing and readable in MQTT Explorer or a log, which makes commissioning and debugging easier.
  • Optional per-tag PLC timestamp (tag:value:epoch_ms), which the bridge already parses.
  • The bridge ingests the lines directly, skipping the publish-map expansion (from the bridge code).

Cons

  • @@bytes_ratio@@× the bytes when sending everything (@@tv_bytes_kb@@ vs @@pm_bytes_kb@@ KB), so sending takes @@tv_send_ms@@ ms instead of @@pm_send_ms@@ ms at QoS 0 (@@tv_send1_ms@@ vs @@pm_send1_ms@@ ms at QoS 1). That fits a one-second publish, but not two publishes a second on a 50 ms task.
  • About 35 KB more PLC memory: tag names on the PLC and a bigger buffer.
  • @@build_extra_pct@@% more build time when sending everything (@@tv_build_ms@@ vs @@pm_build_ms@@ ms).
  • Tag names in the PLC must match the bridge's tag keys exactly (case-sensitive); they need to be generated from the same config sheet.
  • With RBE, a bridge restart leaves quiet tags unknown until the next full refresh.
  • Multi-line tag:value ingest through the bridge hasn't been tested end to end.

publish_map groups

Pros

  • Smallest message (@@pm_bytes_kb@@ KB) and fastest send (@@pm_send_ms@@ ms at QoS 0), leaving room to publish more often than once a second.
  • No tag names on the PLC; less memory.
  • Slightly cheaper to build (@@pm_build_ms@@ ms).
  • Proven on site today, and the bridge's publish map already exists.

Cons

  • Position coupling: the PLC's value order must match the bridge's publish map exactly. A wrong count rejects the whole line (publish_map_value_count_mismatch); a wrong order silently files values under the wrong tags.
  • Every tag change means editing the PLC and the publish map together.
  • Can't report by exception per tag; at best per group, which saves little when changes are spread out.
  • Unreadable without the map, so harder to debug from raw MQTT.

Either way

  • Build once per publish, never every scan, and spread a 2,000-tag build over several scans (worst scan @@pm_worst_spread_ms@@–@@tv_worst_spread_ms@@ ms instead of @@tv_worst_one_ms@@ ms) or give MQTT its own lower-priority task.
  • Append with a pointer (AppendZ), never CONCAT on the running total, and never pass the payload through a STRING(255).
  • Snapshot the values at the start of a build so a message spread over scans is consistent.
