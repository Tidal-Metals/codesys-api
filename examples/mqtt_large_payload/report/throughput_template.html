Motivation

The next system has about 2,000 tags, and we want to publish them as plain tag:value lines rather than through the publish map. With report-by-exception most messages are small, but a full refresh carries every tag: at start-up, after a reconnect, once a minute, and whenever the bridge needs a full picture. That message is @@message_kb@@ KB for 2,000 tags and about five times that for 10,000.

Measured on this PLC, a full refresh took @@t1_ms@@ ms with the 50 ms task the demo uses, and would take about twice that on the 100 ms comms task the redesign proposes. While it is in flight, no newer data can go out. At 10,000 tags a full refresh would take over three seconds, longer than the publish period. The question was whether that is a hard limit of the library or the protocol, or just a matter of how the library is called.

How a publish travels

Four layers handle a message between your STRING and the broker. Only one of them copies the payload inside the PLC program, and it can only copy 4 KB at a time.

  • Nothing runs between scans. The library has no task of its own. It advances only when your program calls MqttLink.clientFB(...), and the demo and BCNF call it once per scan.
  • The payload is read in place. MQTTPublish keeps the address and length of your STRING; the client copies from it piece by piece as buffers free up. That's why the buffer has to stay untouched until done, and why the library has no 255-character limit.
  • QoS 0 done means handed over, not received: the client reports done when the last piece is in its send buffer. QoS 1 waits for the broker's PUBACK, which the client reads in a later call; the same message took @@qos1_ms@@ ms instead of @@t1_ms@@.

Call by call

Each client call does one step. A buffer is filled and handed to the socket in one call; the TCP layer only notices the send is complete on the next call, and only then marks the buffer empty. The client decides whether it may fill the buffer at the start of each call, before the TCP layer runs, so a freed buffer waits for the call after. One buffer per two calls, and the calls come once per scan.

With one call per scan the message spends nearly all of its @@t1_ms@@ ms waiting: each scan the client works for 2 ms or less, then nothing happens for the rest of the 50 ms. With 16 calls per scan the fourteen calls the message needs run back to back in one scan (@@c16_ms@@ ms of client time), and done shows up in the next.

Why parallel publishers don't help

The fix: more client calls per scan

The demo's PLC_PRG got a setting, ClientCallsPerScan, writable online. The 2,000-tag scale test then published its @@message_kb@@ KB message once a second at QoS 0 for 30 s per setting. "Send to done" counts from the scan that sets send to the one that sees done.

  • Time drops almost exactly with the number of calls until the whole message fits in one scan, at 16 calls. Beyond that the two-scan minimum (send, then done) is the floor; 32 calls only add idle calls.
  • Nothing was lost. At 16 calls a subscriber on the HQ broker checked every message for 75 s: @@verify_messages@@ messages, @@verify_values@@ values, all correct, no gaps.
  • The cost moves, it doesn't grow. Sending the message takes about @@cpu_message_ms@@ ms of client time either way. At one call per scan that is spread over @@t1_scans@@ scans; at 16 calls it is @@c16_ms@@ ms in one scan, which a control task can't absorb but a comms task can.

Recommendations

  • Keep the MQTT client in the comms task, below the control task's priority, as the redesign proposes. Its extra calls can then take milliseconds without delaying control.
  • Use the adaptive loop with a budget of about 5 ms per scan and at most 16 calls. That sends a 2,000-tag full refresh in about @@b5_ms@@ ms and leaves idle scans at one call.
  • Size by bytes, not tag count. About @@kb_per_ms@@ KB per ms of client time; budget ms per scan × scans per second gives the sustained rate.
  • Stay at QoS 0 for bulk data unless a lost message matters; QoS 1 adds a broker round trip, @@qos1_scans@@ scans instead of @@t1_scans@@ here.
  • Don't add publishers or connections for throughput. They share the buffer, or add idle cost and lose ordering.
  • Leave the library as it is. A larger buffer or a refill in the same call would mean maintaining a fork of a compiled library for a gain the call loop already delivers.

Method

  • Bench PLC P2CDS-622 at HQ, demo project mqtt_large_payload_demo, 50 ms task, broker at 192.168.50.240, QoS 0 unless noted. Code and scripts are in the codesys-api repo under examples/mqtt_large_payload/; results in results/throughput/.
  • Fixed calls: measure_scale.py --client-calls N --ungated equivalent (the first runs used a fixed FOR loop). Adaptive: measure_scale.py --client-calls 32 --budget-us B. Idle: measure_idle_client.py. Copy: PLC_PRG.IsCopyBenchRequested. Delivery: verify_scale.py on the broker.
  • Send-to-done times are the last message's; across 28–30 messages per run the worst was within 4 ms of it. Client times are the worst scan in the window.
  • The socket-send time is inferred, not measured directly: the worst one-call client time minus the idle call and the copy.
